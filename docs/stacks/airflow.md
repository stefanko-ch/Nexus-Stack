## Apache Airflow

![Apache Airflow](https://img.shields.io/badge/Apache_Airflow-017CEE?logo=apacheairflow&logoColor=white)

**DAG-based workflow orchestration — the industry standard, with the largest operator and provider ecosystem**

Airflow describes a workflow as a Python DAG: tasks, the dependencies between them, and a schedule. It then runs, retries and records every run, and shows the whole history in a web UI. Features include:

- Python DAGs with the TaskFlow API (`@dag`, `@task`) or classic operators
- Hundreds of provider packages: Postgres, S3, dbt, Spark, Kubernetes, HTTP and more
- Cron, data-interval and asset-driven scheduling, backfills and manual runs
- Deferrable operators that wait on external systems without holding a worker slot
- Grid, graph and Gantt views of every run, with per-task logs
- A versioned REST API (`/api/v2`) for everything the UI does

### Why alongside Dagster, Kestra, Prefect and Windmill

None of those is replaced. Airflow is the orchestrator most job postings, tutorials and community DAGs assume, and it has the broadest connector ecosystem. Writing the same pipeline as an Airflow DAG and as a Dagster asset graph is a better lesson in what "orchestration" means than either one alone.

### Architecture

Airflow 3 split the old webserver into several processes. The stack runs them as upstream's own compose file does, minus Celery and Redis:

| Container | Purpose |
|-----------|---------|
| **airflow-init** | One-shot: `airflow db migrate`, then creates the admin user (or resets its password), then exits |
| **airflow** | The api-server: web UI, REST API, and the Execution API that running tasks call back to |
| **airflow-scheduler** | Schedules DAG runs and — with the LocalExecutor — runs their tasks as subprocesses |
| **airflow-dag-processor** | Parses DAG files and writes them to the metadata database |
| **airflow-triggerer** | Runs deferred operators |
| **airflow-db** | Dedicated PostgreSQL 17, reachable only on the stack's internal network |

The api-server container is named `airflow` because the deploy verifies a stack started by looking for a container with exactly the service's name.

Every long-running component waits for `airflow-init` to exit successfully. If the migration or the user setup fails, nothing else starts — the image's built-in `_AIRFLOW_DB_MIGRATE` switch is deliberately not used, because its entrypoint runs `airflow db migrate || true` and would let the stack start on a broken schema.

Tasks run inside `airflow-scheduler`, which is on `app-network`, so a task can reach other stacks by container name (for example `postgres:5432` or `minio:9000`). The scheduler's memory limit (3 GB) is what all concurrently running tasks share; `AIRFLOW__CORE__PARALLELISM` caps them at 8.

### Credentials

```
Infisical → airflow → AIRFLOW_USERNAME      = ADMIN_USERNAME
                      AIRFLOW_PASSWORD      (generated)
                      AIRFLOW_DB_USERNAME   nexus-airflow
                      AIRFLOW_DB_PASSWORD   (generated)
```

Sign in to `https://airflow.<domain>` with `AIRFLOW_USERNAME` / `AIRFLOW_PASSWORD` after passing Cloudflare Access.

**Why a second login behind Access**, when stacks such as MLflow rely on Access alone: Airflow 3 always runs an auth manager, and its default, the SimpleAuthManager, is documented upstream as "intended for development and testing". The stack uses the FAB auth manager with a real admin account instead.

`airflow-init` runs on every stack start and resets the admin password to the rendered value if the user already exists. The login therefore always matches Infisical, even if a database survived a credential rotation.

Three further values are generated by OpenTofu and written only to the stack's `.env` (mode `0600`), not to Infisical: the JWT secret, the API secret key, and the Fernet key that encrypts connection passwords stored in Airflow. All five Airflow containers must share them — with differing JWT secrets the stack reports healthy and every task fails with `403 Invalid auth token`.

> **A DAG author can read those three values, and the database URL.** With the `LocalExecutor` each task runs as a subprocess of `airflow-scheduler` and inherits its environment, so any DAG can print `AIRFLOW__CORE__FERNET_KEY`, `AIRFLOW__API_AUTH__JWT_SECRET`, `AIRFLOW__API__SECRET_KEY` and `AIRFLOW__DATABASE__SQL_ALCHEMY_CONN`. That is enough to decrypt every stored connection password, sign task tokens, and reach the metadata database directly.
>
> This is a property of the executor, not an oversight: only a `CeleryExecutor` or `KubernetesExecutor` puts tasks in their own process space, and both need broker or cluster infrastructure this project deliberately does not run. The admin password is the one credential kept out — it is passed to `airflow-init` alone, which is why the compose file sets no `env_file`.
>
> **Treat write access to the DAG folder as equivalent to full access to this Airflow.** That is the same trust boundary the rest of the stack assumes, since the DAG folder is reachable only over SSH through the tunnel.

### Adding DAGs

DAGs live in the Docker volume `airflow_dags`, mounted at `/opt/airflow/dags` in every component. **Nothing syncs DAGs from Git yet** — for now, copy a file in over SSH:

```bash
scp my_dag.py nexus:/tmp/
ssh nexus "docker cp /tmp/my_dag.py airflow-dag-processor:/opt/airflow/dags/"
```

The DAG processor rescans the folder for new files every 300 seconds (`[dag_processor] refresh_interval`, the image default), so a new DAG can take up to five minutes to appear. New DAGs start paused (`DAGS_ARE_PAUSED_AT_CREATION`); unpause one in the UI before triggering it. Airflow's example DAGs are not loaded.

A minimal DAG to check the setup end to end:

```python
from airflow.sdk import dag, task
import pendulum


@dag(schedule=None, start_date=pendulum.datetime(2026, 1, 1), catchup=False)
def nexus_smoke():
    @task
    def hello():
        print("hello from Airflow")

    hello()


nexus_smoke()
```

### Behind Cloudflare Tunnel

Three settings make the api-server work behind the tunnel; each is commented in `stacks/airflow/docker-compose.yml`:

- **`AIRFLOW__API__BASE_URL=https://airflow.<domain>`** — the public URL used for generated links and login redirects.
- **`AIRFLOW__CORE__EXECUTION_API_SERVER_URL=http://airflow-api-server:8080/execution/`** — tasks report their state to the api-server. The default is derived from the base URL, which here is the Access-protected public hostname a task cannot pass, so tasks use the internal network instead.
- **`api-server --proxy-headers` with `FORWARDED_ALLOW_IPS=*`** — lets the api-server see that the browser is on https, so its auth cookie is set `Secure`. Without either, login still works but the cookie is not marked `Secure`.

### What survives a teardown

Checked against `src/nexus_deploy/s3_restore.py`: Airflow is **not** in `standard_targets()`.

- **`rebuild` mode:** the metadata database (run history, connections, variables, users), the DAGs volume and the task logs are destroyed with the server. The next spin-up starts an empty Airflow with a freshly created admin user. Keep DAGs somewhere else — in Git — and treat connections and variables as configuration to recreate.
- **`snapshot` mode:** all three are named Docker volumes on the server's root disk, which the snapshot images, so they come back as they were.

### Quick check

The tunnel hostname sits behind Cloudflare Access, so check from the server, where the port is bound to loopback:

```bash
ssh nexus "curl -s http://127.0.0.1:8104/api/v2/monitor/health"
```

The response reports `metadatabase`, `scheduler`, `triggerer` and `dag_processor`, each with `"status": "healthy"` once the stack is up. `docker ps` shows five running Airflow containers plus `airflow-init` as exited with code 0.

### Troubleshooting

- **Nothing but `airflow-db` and `airflow-init` exist** — `airflow-init` exited non-zero, and every other component waits for it. `ssh nexus "docker logs airflow-init"` shows whether the migration or the user setup failed.
- **Tasks go straight to failed, logs mention `Invalid auth token`** — the components disagree on the JWT secret. No container reads the `.env` itself: Compose interpolates `/opt/docker-server/stacks/airflow/.env` when the stack comes up and injects `AIRFLOW__API_AUTH__JWT_SECRET` into each container's environment. A changed value therefore reaches a container only through a recreate — restart the whole stack, not a single container.
- **A new DAG does not appear** — wait out the 300-second refresh interval, then check the DAG processor for import errors: `ssh nexus "docker logs airflow-dag-processor"`.
