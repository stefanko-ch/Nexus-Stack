## InfluxDB

![InfluxDB](https://img.shields.io/badge/InfluxDB-22ADF6?logo=influxdb&logoColor=white)

**Time-series database with retention policies, downsampling tasks and a built-in UI**

InfluxDB stores measurements over time and gives them a lifecycle: buckets carry their own retention, tasks downsample on a schedule, and tokens scope what each client may touch. Features include:

- Web UI with a query builder, dashboards and a task editor
- Flux — a dataflow query language built for time-series reshaping
- Buckets with retention: data ages out on a schedule, without a cron job
- Tasks: scheduled Flux that downsamples raw points into rollups
- Token-based auth with per-token read/write scopes
- Accepts the InfluxDB line protocol, so [Telegraf](telegraf.md) writes to it unchanged

### Why alongside QuestDB

[QuestDB](questdb.md) is already here, is also a time-series database, and **also** accepts the InfluxDB line protocol — so this is not "the missing sink for Telegraf". Telegraf can write to either.

The difference is what happens after the write. QuestDB is SQL-first over the PostgreSQL wire: familiar clients, familiar language, and you manage lifecycle yourself. InfluxDB is the one where retention is a property of the bucket and downsampling is a task the database runs. Pointing Telegraf at each in turn, then asking what changed, is a better exercise than reading a comparison table.

### Credentials

Both the admin password and the admin token are generated by OpenTofu per deployment and pushed to Infisical. Neither is ever printed to a workflow log.

```
Infisical → influxdb → INFLUXDB_ADMIN_USERNAME   nexus-influxdb
                       INFLUXDB_ADMIN_PASSWORD   (generated)
                       INFLUXDB_ADMIN_TOKEN      (generated)
```

The username is stored alongside the secrets deliberately: a reader holding only the password would otherwise try `admin`, which is exactly the guessable default the `nexus-` convention exists to prevent.

The **token**, not the password, is what API clients and Telegraf use. The password is only for signing in to the web UI.

### First run

The container starts in `DOCKER_INFLUXDB_INIT_MODE=setup`, so the organisation, bucket, admin user and token are created on first boot from the environment. Without it InfluxDB would sit in an onboarding state answering 401 to everything until somebody completed a wizard by hand — which nobody would, on a stack that is torn down and rebuilt.

Setup runs once. On a later spin-up the volume already holds an initialised database and the init variables are ignored.

### Writing from Telegraf

Telegraf currently writes to `outputs.prometheus_client`. To send to InfluxDB instead, add to `stacks/telegraf/telegraf.conf`:

```toml
[[outputs.influxdb_v2]]
  urls = ["http://influxdb:8086"]
  token = "$INFLUXDB_ADMIN_TOKEN"
  organization = "nexus"
  bucket = "default"
```

Note `influxdb:8086` — the container port, not the published `8102`. Other stacks on `app-network` reach it the same way.

### Quick check

```bash
curl -s https://influxdb.<domain>/health | jq '.status'
```

`/health` answers 200 with `"pass"` once the node is ready, and 503 before that. The container's healthcheck whitelists 200 rather than using `curl -f`, so a response that proves the service is up is never read as a failure (#783).
