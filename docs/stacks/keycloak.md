## Keycloak

![Keycloak](https://img.shields.io/badge/Keycloak-4D4D4D?logo=keycloak&logoColor=white)

**Identity and access management — OpenID Connect, OAuth 2.0 and SAML**

Keycloak is an open-source identity provider. It manages realms, clients, users, groups and roles, issues OpenID Connect and OAuth 2.0 tokens and SAML assertions, and can broker other identity providers or federate an existing user directory. Features include:

- Realms as isolated tenants, each with its own users, clients and login theme
- OpenID Connect, OAuth 2.0 (including client credentials and device flow) and SAML 2.0
- Identity brokering (log in with another OIDC/SAML provider) and LDAP/Kerberos user federation
- Fine-grained roles, groups and client scopes
- An admin console and a REST admin API

In Nexus-Stack it is a self-contained IdP to build and test SSO against. **It does not replace Cloudflare Access**, which stays in front of `keycloak.<domain>` like every other stack — see [What an OIDC client would face](#what-an-oidc-client-would-face). No other stack is wired to it.

| Setting | Value |
|---------|-------|
| Host Port | `8106`, bound to `127.0.0.1` (the container keeps Keycloak's own `8080`) |
| Management Port | `9000` inside the container, **not** published on the host |
| Suggested Subdomain | `keycloak` |
| Public Access | No (Cloudflare Access via email OTP) |
| Admin Username | the deployment's `ADMIN_USERNAME` (default `nexus`) |
| Admin Password | Generated per deployment — in Infisical under `keycloak` |
| Backing DB | Dedicated Postgres 17 (`keycloak-db` container, user `nexus-keycloak`) |
| Docker image | [`quay.io/keycloak/keycloak:26.7.3`](https://quay.io/repository/keycloak/keycloak) (`linux/amd64` and `linux/arm64`) |
| Website | [keycloak.org](https://www.keycloak.org) |
| Source | [GitHub](https://github.com/keycloak/keycloak) |

### Usage

1. Enable **Keycloak** in the Control Plane → Spin Up.
2. Open `https://keycloak.YOUR_DOMAIN` → Cloudflare Access email OTP → Keycloak's admin console.
3. Sign in to the **master** realm with the credentials from Infisical (folder `keycloak`).
4. Create a realm of your own for applications. The master realm is for administering Keycloak itself.

### Credentials

```
Infisical → keycloak → KEYCLOAK_ADMIN_USERNAME   same as ADMIN_USERNAME
                       KEYCLOAK_ADMIN_PASSWORD   (generated)
                       KEYCLOAK_DB_USERNAME      nexus-keycloak
                       KEYCLOAK_DB_PASSWORD      (generated)
```

Both passwords are generated by OpenTofu (`random_password.keycloak_admin_password`, `random_password.keycloak_db_password`) and pushed to Infisical. Like every credential in Infisical they are also synced into Kestra as `SECRET_*` environment variables — a property of the project, not of this stack (#716).

### The bootstrap admin is created once

The admin account comes from `KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD`, and Keycloak reads them **only when it creates the master realm** — the first start against an empty database. On that start it logs:

```
KC-SERVICES0077: Created temporary admin user with username nexus
```

Measured on 26.7.3: after a `--force-recreate` with a *different* `KC_BOOTSTRAP_ADMIN_PASSWORD`, the original password still returned a token and the new one got `invalid_grant`. Changing the environment does not change the password of an existing admin.

The two lifecycles do not produce a mismatch on their own:

- **`rebuild`** — the teardown runs an untargeted `tofu destroy`, so both passwords are regenerated, and the database is gone with the server (see [Persistence](#persistence)). The next start bootstraps a fresh realm with the new password, matching Infisical.
- **`snapshot`** — the teardown destroys only `hcloud_server.main`, so the passwords survive in OpenTofu state, and the disk image brings the database back. Nothing changes.

It becomes possible if the database survives while the password is regenerated — for example by replacing `random_password.keycloak_admin_password` by hand. Then Infisical shows a password Keycloak never saw; change it inside Keycloak.

Keycloak labels this account *temporary*. If you create a permanent admin and delete it, remember that Infisical still lists the bootstrap credentials, which then no longer work.

### Configuration choices

All set as environment variables in `stacks/keycloak/docker-compose.yml`. Option names were checked against `kc.sh start --help-all` of the pinned image, not against older documentation: the hostname options changed across the 2x releases, and in 26.x only hostname v2 exists.

| Variable | Value | Why |
|---|---|---|
| `KC_HOSTNAME` | `https://keycloak.<domain>` | A full URL, so scheme and port are fixed rather than guessed from the request. The container sees plain HTTP on 8080; the browser uses HTTPS on 443. This is the `iss` of every token. |
| `KC_HOSTNAME_BACKCHANNEL_DYNAMIC` | `true` | Token, userinfo and JWKS endpoints follow the URL the request arrived on, so a container can use `http://keycloak:8080`. |
| `KC_HTTP_ENABLED` | `true` | TLS terminates at Cloudflare; the tunnel speaks HTTP to the origin. |
| `KC_PROXY_HEADERS` | `xforwarded` | See below. |
| `KC_CACHE` | `local` | Production mode defaults to a clustered cache with `jdbc-ping` discovery. One node has nobody to cluster with. |
| `KC_HEALTH_ENABLED` | `true` | For the container healthcheck, on port 9000. |

**Why `KC_PROXY_HEADERS` is needed**, measured with a request shaped like the tunnel's (`Host: keycloak.example.com`):

```
with    X-Forwarded-Proto: https  -> token_endpoint https://keycloak.example.com/realms/master/protocol/openid-connect/token
without                            -> token_endpoint http://keycloak.example.com/realms/master/protocol/openid-connect/token
issuer, both cases                 -> https://keycloak.example.com/realms/master
```

Cloudflare documents adding `X-Forwarded-Proto` and `X-Forwarded-For` to requests it sends to an origin. The trade-off is that no `KC_PROXY_TRUSTED_ADDRESSES` is set, so a container on `app-network` can send these headers too and Keycloak records whatever client address they claim.

**Why not `--optimized`.** `KC_DB`, `KC_CACHE` and `KC_HEALTH_ENABLED` are build-time options, so a plain `start` re-augments the server before booting. Measured: `Quarkus augmentation completed in 2896ms` on first start, `3090ms` after a `--force-recreate`, then the server itself up in about 2 s. A custom image built with `kc.sh build` would save those ~3 s per start, at the cost of a Dockerfile to build on the server and keep in step with every version bump.

**Health.** `/health/ready` is served on the management port, not on 8080 (`8080/health/ready` → 404). Port 9000 is not published on the host, so it is unreachable through the tunnel; containers on `app-network` can reach it (`keycloak:9000/health/ready` → 200). Metrics are not enabled. The image ships no `curl` or `wget`, so the healthcheck sends a raw HTTP request over `/dev/tcp`.

### Persistence

`keycloak-db` keeps its data at `/mnt/nexus-data/keycloak/db` on the server.

- **`snapshot` lifecycle:** survives a teardown, because the whole disk is imaged.
- **`rebuild` lifecycle:** **does not survive.** Keycloak is not in `standard_targets()` in `src/nexus_deploy/s3_restore.py`, so nothing dumps it before the server is destroyed. Every realm, client and user you created is gone after the next teardown, and the next spin-up starts with an empty master realm.

If Keycloak holds configuration you want to keep under `rebuild`, export the realm before the teardown — from the admin console, or with the image's `kc.sh export` command — and keep the file somewhere that survives, such as your Forgejo workspace repository. Adding Keycloak to the R2 dump list is a separate change.

### What an OIDC client would face

Nothing in Nexus-Stack is connected to Keycloak yet (Lakekeeper's OIDC mode is tracked in #834). Anyone wiring a client should know these, all measured against this configuration unless stated otherwise:

1. **The issuer is always the public URL.** Discovery fetched from inside `app-network` returns:

   ```
   GET http://keycloak:8080/realms/master/.well-known/openid-configuration
   issuer                  https://keycloak.example.com/realms/master
   authorization_endpoint  https://keycloak.example.com/realms/master/protocol/openid-connect/auth
   token_endpoint          http://keycloak:8080/realms/master/protocol/openid-connect/token
   jwks_uri                http://keycloak:8080/realms/master/protocol/openid-connect/certs
   ```

   A backend on `app-network` can therefore use the internal URL for token exchange and JWKS, but must accept `https://keycloak.<domain>/realms/<realm>` as `iss`. The OpenID Connect Discovery specification requires the issuer to match the URL discovery was fetched from, so a client library that enforces that will reject the internal URL unless it lets you set the issuer separately (not verified per library).

2. **The browser half goes through Cloudflare Access.** `authorization_endpoint` is on the public hostname, and that hostname has an Access application in front of it (`tofu/stack/main.tf` creates one for every non-public service). A user is sent through Access's email OTP before they ever see Keycloak's login page — two logins, the first of which is not Keycloak's.

3. **A server-side call to the public hostname gets Access, not Keycloak.** Anything that fetches discovery or JWKS from `https://keycloak.<domain>` without an Access session receives Access's login page instead of JSON — the same failure [lakekeeper.md](./lakekeeper.md) describes for PyIceberg. Use the internal URL from point 1, or give the caller an Access service token; neither is set up here.

4. **Making the hostname `public: true` is not the answer by default.** `tests/unit/test_stack_conventions.py` allows exactly one public service (`git-proxy`), and the admin console lives on the same hostname as the login pages.

### Quick check

The tunnel hostname sits behind Cloudflare Access, so check from the server:

```bash
ssh nexus "docker ps --filter name=keycloak --format '{{.Names}} {{.Status}}'"
```

Both `keycloak` and `keycloak-db` should show `(healthy)`.

### Upgrading

The version appears in two places that must move together: `image:` in `services.yaml` and the `${IMAGE_KEYCLOAK:-…}` fallback in the compose file. `test_compose_fallbacks_match_the_declared_version` catches a mismatch. Keycloak migrates its database schema on start (26.7.3 logged `Initializing database schema` against an empty database). Under the `rebuild` lifecycle there is no data to migrate; under `snapshot`, take the upgrade notes for the target version seriously, because the migration runs against your realms.
