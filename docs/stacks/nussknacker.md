## Nussknacker

![Nussknacker](https://img.shields.io/badge/Nussknacker-1E88E5?logo=apacheflink&logoColor=white)

**Visual low-code designer for stream processing — draw a scenario, deploy it to Flink**

Nussknacker lets you build real-time decision logic by drawing it: source, filters, enrichments, sink, connected on a canvas and deployed to Flink as a running job. Features include:

- Drag-and-drop scenario authoring with a typed expression language (SpEL)
- Deployment to the existing [Flink](flink.md) cluster — Nussknacker submits the job, Flink runs it
- Kafka sources and sinks against the existing [Redpanda](redpanda.md) broker, with schema introspection
- Scenario versioning, deployment history and per-node counts in the UI
- A test mode that replays sample events through a scenario before deploying it

### Why alongside Dinky

[Dinky](dinky.md) is already here and also submits jobs to the same Flink cluster. Both stay, because they are for different people:

| | Dinky | Nussknacker |
|---|---|---|
| Interface | Flink SQL IDE | Visual canvas |
| Audience | Developers | Domain experts |
| Artefact | SQL statements | Scenario graph |

Running the same pipeline down both paths — the same filter written once as SQL and once as a drawn node — is a better lesson than either on its own.

### The demo accounts are removed

This is the part worth knowing about. The image ships a `users.conf` with **five accounts whose passwords equal their usernames**:

```text
admin/admin   reader/reader   writer/writer   deployer/deployer   demo/demo
```

`admin` with an `Admin` role and `isAdmin: true`. Left alone, anyone who reaches the UI is an administrator.

The stack replaces all five. `AUTHENTICATION_USERS_FILE` points at a file rendered by `service_env._render_nussknacker` containing a single account, `nexus-nussknacker`, with a password generated by OpenTofu and pushed to Infisical. Verified against the image: with that file in place, `admin:admin` answers **401** and so do the other four.

The file is rendered rather than committed with a placeholder because **Nussknacker parses it without environment substitution** — a `users.conf` containing `${NUSSKNACKER_ADMIN_PASSWORD}` makes the container exit 1 during startup, in `AuthenticationConfiguration.usersOpt`. It is written mode `0600`, since the password is in cleartext, and bind-mounted read-only.

### Wiring

Three environment variables, read by the shipped `application.conf`. No configuration file is mounted for these:

```yaml
FLINK_REST_URL:      http://flink-jobmanager:8081
KAFKA_ADDRESS:       redpanda:9092
SCHEMA_REGISTRY_URL: http://redpanda:8081
```

The Kafka and schema-registry endpoints are taken from [Redpanda Console's](redpanda-console.md) own configuration rather than from documentation — that is what demonstrably works against this deployment.

**Flink and Redpanda must be enabled** for scenarios to deploy or read anything. Nussknacker's UI starts without them, so the failure appears at deployment time rather than at boot.

### One container, no companion database

The Designer keeps its state — users, scenarios, deployment history — in an embedded HSQLDB under `/opt/nussknacker/storage`, created on first boot and migrated by Flyway. No PostgreSQL companion is deployed.

That state is in the `nussknacker_storage` volume. Under the `rebuild` lifecycle the volume does not survive a teardown, so **scenarios are lost** unless they were exported; under `snapshot` it does. See [the lifecycle concept](../concepts/lifecycle.md) for which stacks the R2 layer covers — Nussknacker is not among them.

### Memory

Measured at **794 MB** idle on first boot, settling around 726 MB. The limit is 1500 MB. It is a JVM service and it is not small: on the 16 GB `cx43` it sits comfortably beside Flink and Kestra, but it is a reasonable candidate to disable when streaming is not the focus of a session.

### Version pinning

Pinned to `1.18.1_scala-2.13`, published 2024-12-09 and multi-arch (`linux/amd64`, `linux/arm64`).

Worth knowing before bumping: the project is actively developed — the repository saw commits this week — but **has not cut a stable release since `v1.18.1`**. Every newer Docker tag is a `SNAPSHOT`, `preview` or `staging` build. The Scala suffix is part of the tag, not a variant: `1.18.1` and `1.18.1_scala-2.13` are different tags.

The Designer runs Flyway migrations against its own database on start, so a version bump is a schema change against populated state. Test it on a copy before doing it on something you care about.
