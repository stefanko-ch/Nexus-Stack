## Planka

![Planka](https://img.shields.io/badge/Planka-4D4D4D?logo=planka&logoColor=white)

**Open-source kanban board (Trello alternative) with real-time collaboration**

Planka is a self-hosted kanban board for project and task management. Organize work into boards, lists, and cards with labels, due dates, checklists, attachments, and Markdown descriptions. Real-time multi-user collaboration, comments, and activity tracking — backed by a dedicated PostgreSQL database.

| Setting | Value |
|---------|-------|
| Default Port | `1337` (→ container 1337) |
| Suggested Subdomain | `planka` |

### Usage

1. Enable **Planka** in the Control Plane → Spin Up
2. Open `https://planka.YOUR_DOMAIN` → CF Access email OTP → Planka login form
3. Sign in with the seeded admin account:
   - **Email**: your `ADMIN_EMAIL` (the same email used as the Infisical / Cloudflare Access identity)
   - **Password**: `infisical secrets get PLANKA_PASSWORD --path=/planka --plain`
4. Create your first project and board, then invite work into lists and cards

### Auth model

Two-layer auth, both enforced:

1. **Cloudflare Access** at the edge (email OTP) gates who reaches the Planka login page at all.
2. **Planka's own login** with a single seeded admin account is the in-app identity. Planka seeds this account on first boot from the `DEFAULT_ADMIN_*` env vars; setting `DEFAULT_ADMIN_EMAIL` also marks it as a protected account (can't be edited/deleted from the UI).

Unlike HedgeDoc (which needs a post-boot CLI hook to seed its admin), Planka creates the admin itself at startup — no `services.py` hook required. Additional users can be invited from within Planka; they hit the same CF Access OTP at the edge first.

### Secrets

Generated by OpenTofu (`random_password.planka_secret_key`, `random_password.planka_db_password`, `random_password.planka_admin`) and pushed to Infisical under folder `/planka`:

- `PLANKA_USERNAME` — admin email (same as your `ADMIN_EMAIL`)
- `PLANKA_PASSWORD` — admin login password (24 chars)
- `PLANKA_SECRET_KEY` — signs sessions + tokens (64 chars)
- `PLANKA_DB_PASSWORD` — Postgres password for the dedicated `planka-db` container

All four must be non-empty or the deploy aborts with a clear `ServiceEnvError` (no silent broken-sessions / DB-auth-failure / no-admin fallback).

### Persistence

- `planka-db` Postgres → captured via `pg_dump` (`PostgresDumpTarget(container="planka-db", database="planka", user="nexus-planka")`) — boards, lists, cards, users, and comments live here
- `/mnt/nexus-data/planka/data` bind-mount → captured via `rsync` (`RsyncTarget(name="planka-data", s3_subpath="planka/data")`) — Planka 2.x stores all uploaded files (attachments, avatars, background images, favicons) under a single `/app/data` directory

Both targets live in `src/nexus_deploy/s3_restore.py::standard_targets` and run on every `teardown` (push to R2) + `spin-up` (restore from R2). Boards and attachments survive teardown cycles without operator intervention.

The data bind-mount path is mkdir+chowned to `1000:1000` (the in-container `node` user) by `compose_runner.render_remote_script`'s `planka_data_prep` block before the compose-up runs, so first-upload doesn't fail with EACCES.

### Troubleshooting

- **"This site can't be reached"**: CF Access cookie expired — refresh, do OTP again
- **Login fails / "invalid credentials" right after first deploy**: Planka only seeds the admin on the *first* boot against an empty database. If you changed `PLANKA_PASSWORD` after the DB already existed, the in-DB hash won't match — reset it from a shell: `docker exec -it planka npm run console` (or restore from a fresh DB). Check `docker logs planka | grep -i admin` to confirm the seed ran.
- **Real-time updates not syncing**: Planka uses WebSockets for live board updates. Cloudflare Tunnel allows WebSockets by default for the ingress rules nexus-stack provisions. If updates only appear on reload, check `docker logs planka` for socket errors (usually a client-side WS-upgrade failure from an ad-blocker / network filter).
- **Attachment uploads fail**: check `docker logs planka` — usually the `/mnt/nexus-data/planka/data` host dir is full (no resize logic; bump the host disk and restart the container).
