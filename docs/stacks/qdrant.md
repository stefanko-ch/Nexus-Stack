## Qdrant

![Qdrant](https://img.shields.io/badge/Qdrant-DC244C?logo=qdrant&logoColor=white)

**Vector database with a built-in web dashboard, payload filtering and REST + gRPC APIs**

Qdrant is a vector database written in Rust. Collections hold points — a vector plus a JSON payload — and queries combine vector similarity with filters on that payload. Unlike the other two vector stores here it ships a web UI, so a collection can be inspected from the browser rather than only from a client library. Features include:

- A web dashboard at `/dashboard`: browse collections and points, run queries in a console, follow the built-in tutorial
- Payload filtering applied during the search, with payload indexes for the fields you filter on
- Scalar, product and binary quantization, for when an index stops fitting comfortably in memory
- REST on port 6333 and gRPC on port 6334, with Python, TypeScript, Rust and Go clients
- Collection snapshots, written to their own volume

| Setting | Value |
|---------|-------|
| Default Port | `6333` (REST + dashboard, bound to `127.0.0.1` on the host) |
| gRPC Port | `6334` — inside `app-network` only, not published on the host |
| Suggested Subdomain | `qdrant` |
| Public Access | No (protected by Cloudflare Access) |
| Credentials | API key, generated per deployment — see below |
| Persistence | Local Docker volumes (compose keys `qdrant_storage`, `qdrant_snapshots`) |
| Website | [qdrant.tech](https://qdrant.tech) |
| Source | [GitHub](https://github.com/qdrant/qdrant) |

### Why a third vector store

[Chroma](chroma.md) and [Weaviate](weaviate.md) are already here, and all three stay because they teach different things:

| | Chroma | Weaviate | Qdrant |
|---|---|---|---|
| Shape | Small, embedded-style | Schema-first server | Points + payloads |
| Stand-out feature | Fewest concepts to learn | Hybrid BM25 + vector search | Payload filters, quantization |
| Web UI | Swagger at `/docs/` | None | Dashboard at `/dashboard` |
| Own authentication | Off | Off | **API key, on** |

Running the same corpus through each is a useful exercise in what a storage engine's model actually changes.

### Browser entry point

`/` answers a JSON version banner (`{"title":"qdrant - vector search engine","version":"1.19.1",...}`), not a UI. The service's `services.yaml` entry therefore sets **`landing_path: "/dashboard"`**, so the Control Plane's **Open Qdrant** button goes straight to the dashboard — the same mechanism [Chroma](chroma.md) uses to send its button to Swagger.

It is not `api_only`, unlike Weaviate: there is a UI to send the button to.

### Authentication: two layers, on purpose

Qdrant runs with its own API key (`QDRANT__SERVICE__API_KEY`). This is a deliberate difference from Chroma and Weaviate, which leave their own authentication off and rely on Cloudflare Access alone.

| From | Reaches it at | Gated by |
|---|---|---|
| Another container on `app-network` | `qdrant:6333` (REST), `qdrant:6334` (gRPC) | API key |
| The host itself, e.g. over SSH | `127.0.0.1:6333` | SSH, then the API key |
| Anywhere else | `https://qdrant.<domain>` | Cloudflare Access, then the API key |

The Weaviate page states that stack's cost plainly: any container on `app-network` can read and write every collection. Here that is not true — without the key, every collection endpoint answers `401`. The price is one secret that every client has to be given.

Measured on `v1.19.1`, what the key does and does not cover:

| Request | Without key | With key |
|---|---|---|
| `GET /collections`, `/telemetry`, `/metrics` | `401` | `200` |
| gRPC calls on 6334 | `UNAUTHENTICATED` | OK |
| `GET /`, `/dashboard`, `/healthz`, `/livez`, `/readyz` | `200` | `200` |

The dashboard's static files load without the key, but it can do nothing until you give it one.

> **An empty key is not an error to Qdrant.** With `QDRANT__SERVICE__API_KEY=""` it logs that the key "is treated as unset" and serves every collection without authentication. That is why the compose file uses `${QDRANT_API_KEY:?...}` and the deploy refuses to render an empty key, instead of trusting the container to refuse.

### Getting the key

The key is generated by OpenTofu (`random_password.qdrant_api_key`) and stored in Infisical:

| Infisical folder | Key | What it is |
|---|---|---|
| `qdrant` | `QDRANT_API_KEY` | The API key. Qdrant has no user accounts, so there is no username. |

On the server it is also in `/opt/docker-server/stacks/qdrant/.env`, written with mode `0600`.

**In the dashboard:** open Qdrant from the Control Plane, pass the Cloudflare Access login, and the dashboard shows a **Set API Key** dialog. Paste the key and press **Apply**. The dashboard keeps it in the browser's local storage, so you are asked once per browser; the key icon in the top bar changes it later.

**From a client inside the stack** (a notebook, a Kestra task, code-server):

```python
import os
from qdrant_client import QdrantClient, models

client = QdrantClient(
    host="qdrant", port=6333, grpc_port=6334, https=False,
    api_key=os.environ["QDRANT_API_KEY"],   # however your client receives it
    prefer_grpc=True,                        # optional; REST works the same
)
client.create_collection(
    "documents",
    vectors_config=models.VectorParams(size=768, distance=models.Distance.COSINE),
)
```

The key is not injected into any other stack automatically — no notebook or pipeline stack is wired to Qdrant. Pass it in the way you pass other Infisical secrets to that tool.

`qdrant-client` prints `UserWarning: Api key is used with an insecure connection` for this configuration. Inside `app-network` that is expected: the traffic never leaves the Docker network, and outside traffic is HTTPS through the tunnel.

### Quick check

The tunnel hostname is behind Cloudflare Access, so an unauthenticated `curl` from your laptop gets the Access login page rather than JSON. Check from the server, where the port is bound to loopback:

```bash
ssh nexus 'set -a; . /opt/docker-server/stacks/qdrant/.env; set +a; curl -s -H "api-key: $QDRANT_API_KEY" http://127.0.0.1:6333/collections'
```

This reads the key on the server rather than putting it on your local command line. Without the header, the same request answers `Must provide an API key or an Authorization bearer token`.

### gRPC

Port 6334 is not published on the host and has no tunnel ingress rule. In-cluster clients reach it at `qdrant:6334` over `app-network`, which is where the gRPC clients that want it run. The browser URL is REST only.

### Persistence

| Volume (compose key) | Mounted at | Holds |
|---|---|---|
| `qdrant_storage` | `/qdrant/storage` | Collections, indexes, payloads |
| `qdrant_snapshots` | `/qdrant/snapshots` | Collection snapshots you create |

Snapshots get their own volume because Qdrant writes them outside the storage directory. Without it they would live in the container's writable layer and disappear on the next recreate. Docker Compose prefixes both with the project name, so `docker volume ls` shows `qdrant_qdrant_storage` and `qdrant_qdrant_snapshots`.

What survives a teardown depends on the lifecycle mode:

| Lifecycle | Collections | API key |
|---|---|---|
| `rebuild` (`teardown.yml`) | **Lost.** The untargeted `tofu destroy` deletes the server and its disk, and `s3_restore` has no target for Qdrant. | Regenerated along with every other `random_password`. |
| `snapshot` (`teardown-snapshot.yml`) | **Kept.** The Hetzner disk snapshot captures the root disk, which holds Docker's named volumes. | Unchanged — only `hcloud_server.main` is destroyed, so the OpenTofu state keeps the password. |

After a rebuild the dashboard still holds the old key in local storage and reports *"Your API key is invalid. Please, set a new one."* Fetch the new one from Infisical.

A changed key never locks you out of existing data. Measured on `v1.19.1`: a collection created under one key, with the container restarted on the same volume under a different key, is still listed — the old key gets `401`, the new one sees the collection. The key is configuration, not something written into storage. (This is the opposite of [InfluxDB](influxdb.md), which bakes its credentials in on first start.)

For collections that must outlive a rebuild teardown, either switch the stack to the [snapshot lifecycle](../admin-guides/snapshot-lifecycle.md) or rebuild the collection from source on each spin-up — the usual pattern for embeddings, which are derived data.

### Telemetry

`QDRANT__TELEMETRY_DISABLED=true` turns off Qdrant's anonymous usage reporting; the container logs `Telemetry reporting disabled` at start. This is unrelated to the local `/telemetry` endpoint, which still works and requires the key.

### Health

The container's healthcheck sends `GET /readyz` and requires a `200` status line. `/readyz` is exempt from the API key, so the probe needs no secret.

The image ships neither `curl` nor `wget` (verified with `command -v` inside `v1.19.1`), so the probe speaks HTTP over bash's `/dev/tcp`. It checks the status, not just that the port accepts a connection: a probe against `/collections` without the key returns `401` and fails, as does a wrong port or path.
