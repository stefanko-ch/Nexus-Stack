## TimescaleDB

![TimescaleDB](https://img.shields.io/badge/TimescaleDB-FDB515?logo=timescale&logoColor=white)

**PostgreSQL with the TimescaleDB extension — hypertables, continuous aggregates and compression for time-series.**

TimescaleDB is an extension that turns PostgreSQL into a time-series database. It is not a separate engine: the server is PostgreSQL 18, and everything a PostgreSQL client knows keeps working. Features include:

- **Hypertables** — a table partitioned into time-based chunks automatically, queried as one table
- **Continuous aggregates** — materialized rollups that refresh incrementally as new data arrives
- **Native compression** — old chunks converted to a columnar format, typically a fraction of their size
- **Retention policies** — drop chunks older than a threshold, on a schedule the database runs itself
- `time_bucket()` and other time-series SQL functions, next to the whole of PostgreSQL

### Why alongside QuestDB and InfluxDB

[QuestDB](questdb.md) and [InfluxDB](influxdb.md) are both here already, and both are purpose-built time-series engines with their own storage model — QuestDB SQL-first over the PostgreSQL wire, InfluxDB with Flux and bucket retention.

TimescaleDB is the one where time-series data lives **in a real PostgreSQL database**. A sensor reading can be JOINed against a relational `devices` table, constrained with a foreign key, and queried with window functions and CTEs in the same statement. Loading the same data into all three and asking the same question is a useful exercise in what a storage engine's model actually changes.

### Credentials

The superuser password is generated by OpenTofu and pushed to Infisical. It is never printed to a workflow log.

```
Infisical → timescaledb → TIMESCALEDB_USERNAME   nexus-timescaledb
                          TIMESCALEDB_PASSWORD   (generated)
                          TIMESCALEDB_DATABASE   timescaledb
```

The username and database are stored beside the password so a reader holding only the password does not try `postgres`, which is exactly the guessable default the `nexus-` convention exists to prevent.

The password is applied **once**, when the container initialises an empty volume. After that PostgreSQL keeps what it has and ignores the environment variable, like every PostgreSQL image. The two lifecycles do not produce a mismatch on their own: in `rebuild` mode the volume is destroyed along with the server and initialised fresh; in `snapshot` mode the volume and the OpenTofu state survive together. If a `random_password` is ever replaced by hand, change the password inside the database too (`ALTER ROLE "nexus-timescaledb" PASSWORD '…'`).

### Connecting

From any container on `app-network` — notebooks, Grafana, Superset, Kestra:

```
postgresql://nexus-timescaledb:<password>@timescaledb:5432/timescaledb
```

Note `5432`, the container port. `5433` exists only on the host, and only while the firewall rule is open.

From **pgAdmin**, **CloudBeaver** or **Adminer**, add a server with host `timescaledb`, port `5432`, user `nexus-timescaledb`. None of the three is pre-registered with this connection today — pgAdmin's `servers.json` only lists the shared `postgres` stack.

**From outside the server** (DBeaver, DataGrip, `psql` on a laptop):

1. Open the Control Plane **Firewall** page and enable the `timescaledb` rule (port `5433`). Restrict the source IP to your own address.
2. Run **Spin Up**. The deploy adds a `5433:5432` port mapping for the container and a matching Hetzner firewall rule.
3. Connect to `<server-ip>:5433`. No DNS record is created for this rule; see *Firewall Management* in the [stacks overview](README.md).

The connection is not TLS-encrypted — `SHOW ssl` reports `off` in this image — so the password is protected only by PostgreSQL's SCRAM exchange, while query data travels in cleartext. Keep the source-IP restriction tight and close the rule when you are done; it is also reset on every teardown.

### Quick start

```sql
-- A hypertable: an ordinary table, partitioned by time behind the scenes
CREATE TABLE readings (
    time      TIMESTAMPTZ      NOT NULL,
    device_id INTEGER          NOT NULL,
    value     DOUBLE PRECISION
);
SELECT create_hypertable('readings', 'time');

INSERT INTO readings
SELECT now() - i * interval '1 minute', i % 10, random() * 100
FROM generate_series(1, 10000) AS i;

-- An hourly rollup that stays current incrementally
CREATE MATERIALIZED VIEW readings_hourly
WITH (timescaledb.continuous) AS
SELECT time_bucket('1 hour', time) AS bucket, device_id, avg(value)
FROM readings
GROUP BY bucket, device_id;

-- Compress chunks older than a week, on a schedule
ALTER TABLE readings SET (timescaledb.compress, timescaledb.compress_segmentby = 'device_id');
SELECT add_compression_policy('readings', INTERVAL '7 days');
```

### Configuration

**Image variant.** The default image, not `-oss`. The `-oss` build is Apache-2.0-only and refuses compression and continuous aggregates with `functionality not supported under the current "apache" license` — measured on `2.30.0-pg18-oss`. The default build includes those features under the Timescale License, which permits self-hosting.

**Telemetry is off.** `TIMESCALEDB_TELEMETRY=off` makes the image's init script write `timescaledb.telemetry_level=off` and unschedule the telemetry job.

**Tuning.** The image runs `timescaledb-tune` on first start. The compose file pins its inputs rather than letting it guess:

| Variable | Value | Why |
|---|---|---|
| `TS_TUNE_MEMORY` | `2GB` | Matches the container's 2 GB memory limit |
| `TS_TUNE_NUM_CPUS` | `2` | Otherwise it tunes parallelism for all 8 host vCPUs, which every stack shares |
| `TS_TUNE_MAX_CONNS` | `100` | Left unset, it derives 25 for 2 GB — too few once several tools connect |

Resulting settings, measured on `2.30.0-pg18`: `shared_buffers` 640 MB, `effective_cache_size` 1.9 GB, `work_mem` 8 MB, `max_connections` 100, `max_parallel_workers` 2.

⚠️ **Telemetry and tuning both run once, at initialisation.** They live in `/docker-entrypoint-initdb.d`, which the image's entrypoint only executes against an empty data directory. Changing a `TS_TUNE_*` value in the compose file does nothing to an existing volume — run `timescaledb-tune` inside the container, or `ALTER SYSTEM SET …`, instead.

### Data and teardown

The data lives in a named Docker volume on the server's disk. What survives depends on the lifecycle mode:

- **`rebuild` (default): the data does not survive a teardown.** TimescaleDB is not in the R2 backup list (`standard_targets()` in `src/nexus_deploy/s3_restore.py`), so the volume is destroyed with the server and the next spin-up starts with an empty database. Export anything you want to keep first, for example with `pg_dump`.
- **`snapshot`: the data survives**, because the whole disk is imaged.

Under `snapshot`, a future change of the image's PostgreSQL major (the `-pg18` suffix) meets a data directory written by the old one. The deploy's `pg-preflight` phase recognises this image and stops before starting the container, naming both versions and the ways out — see [Snapshot Lifecycle](../admin-guides/snapshot-lifecycle.md). A TimescaleDB *extension* upgrade within the same PostgreSQL major is different: after the new image starts, run `ALTER EXTENSION timescaledb UPDATE;` in each database that uses it, as the first command of a fresh `psql -X` session (upstream's requirement, so no other statement has loaded the old version first).

### Quick check

```bash
ssh nexus "docker exec timescaledb psql -U nexus-timescaledb -d timescaledb -Atc \"SELECT extversion FROM pg_extension WHERE extname = 'timescaledb'\""
```

Prints the installed extension version, `2.30.0`. The container's healthcheck is `pg_isready` — `curl` is not in the image.
